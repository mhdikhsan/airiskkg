## How the three fit together

- **Roles** annotate elements. `pair:playsRole` goes on one BEAM element, and an
  element may carry several roles.
- **Motifs** are the structure a risk pattern reads: role-tagged elements and the
  `beam:use` / `beam:produce` edges between them. A motif is structure only: it makes no
  risk claim, and the AI risk patterns that read it do.
- **AI risk patterns** raise a **candidate risk finding** when a motif match also
  satisfies their applicability conditions. A finding requires triage and is never
  a confirmed defect.

Annotation is per element, and recognition is per combination: a motif matches only
when several correctly tagged elements are wired together in the expected shape.

- **Motifs nest.** A smaller motif can be a subgraph of a larger one and co-matches
  with it, so match counts measure structural coverage and not how many distinct
  things a system does.
- **Motifs cannot express absence.** Matching is monotone, so every "without" or
  "only" claim lives in an applicability condition (glossary R9).
- **Process typing does not decide a match.** Step nodes match on
  `a/rdfs:subClassOf* beam:Process`, so the role is what selects a step.

## 1. Motifs

Motifs are shelved by `pair:motifFamily` and `pair:motifGroup`, a filing decision
about this library that no match query reads. **Carries** lists the risk patterns
declared on the motif. **Realizes** lists the controls it is a candidate structure
for, which is not proof that adding it removes the risk: several realizing motifs
carry risks of their own, so an amended architecture has to be assessed again.

### Declared motifs and what raises a finding

The motifs declared on a risk pattern are the structures the library curates for it.
Most risk queries bind declared pattern nodes, so only those motifs can raise them.
These read roles on any motif match, so a finding can name a motif that is not
declared on the risk pattern: Data and model poisoning, Excessive agency, Improper output handling, Prompt injection, System prompt leakage, Vector and embedding weakness.

**Catalogued, not detected:** `asi10-rogue-agents`. An OWASP agentic entry gets a risk pattern only
when it has a structural signature at design time.

Every finding is a candidate: a structural disposition, never a confirmed failure.

roles under it (`pair:subRoleOf*`), so a role parented to the wrong abstraction is
inert: tagging an element with it silently prevents the match. Categories file the
roles and no query names one. **Shown as** is the name in the workbench picker.

## 4. Data categories (7)

Assign with `pair:containsDataCategory` on a `beam:Data` element. This is the one
facet that is also derived: tag where protected or untrusted content enters, and the
propagation rules below work out where it can reach. There is no personal data
category, deliberately. Personal data is expressed with DPV concepts through
`facet:hasPersonalDataCategory` (glossary R3).

| Category | Definition | Refines |
| --- | --- | --- |
| `ConfidentialInformation` | Content that must be kept secret for operational or business reasons. | `Information` |
| `ExternalUserContent` | Content originating from a user outside the system boundary. | `Information` |
| `GeneratedContent` | Content produced by a generative model rather than authored or retrieved. | `Information` |
| `Information` | Root category for content-kind classification. |  |
| `PromptInstruction` | Instructional content steering model behavior. |  |
| `SensitiveInformation` | Content whose exposure can harm individuals or organizations. | `Information` |
| `UntrustedContent` | Content whose integrity the system cannot vouch for within the submitted graph. |  |

## 5. Annotation guidance (SHACL)

`shacl/annotation_guidance.ttl` asks whether an annotation will actually match
anything. Every shape is `sh:Info` or `sh:Warning`, so it cannot change whether a
graph conforms.

| Shape | Severity | Message |
| --- | --- | --- |
| `AgentMemoryIsALoopShape` | Info | This agent memory store is only written or only read, never both. The Agent Memory Loop motif is constituted by the loop through the store, so a one-way store is an ordinary knowledge source and ASI06 cannot be raised about it. |
| `AgentMessageIsReceivedShape` | Info | This inter-agent message is not consumed by any step playing pair:AgentHandoffStep. The Agent Delegation motif needs both sides of the crossing, so ASI07 cannot be raised about this handoff. |
| `BusinessDataReachesTheArchitectureShape` | Warning | Classified, but it reaches no architecture element: the step that reads it names no AI system, or that system holds no data. |
| `CategoryOnlyShape` | Warning | Tagged with the category {?category} only, so no motif can match it yet. Click it on the canvas and choose a role under {?category}. |
| `DataCarriesARoleShape` | Info | This data element plays no pattern role, so no motif can bind it. That is legitimate for incidental elements, but if it carries user input, retrieved context, a prompt, or model output, annotating it is what makes the surrounding motif matchable. |
| `GenerationStepUsesAModelShape` | Info | This generation step uses no element playing pair:GenerativeModel. Prompted Generation, RAG, and Guardrails all bind the model explicitly, so none of them will match and no generation-side finding can be raised. |
| `KnowledgeSourceDeclaresContentShape` | Info | This knowledge source declares no data category. Whether a store holds sensitive or confidential content is an annotated base fact (Rule R8) - the propagation rules carry it onward but cannot originate it, so sensitive-disclosure findings stay silent until it is stated. |
| `ResourceRoleOnProcessShape` | Warning | This element plays a resource role but is typed beam:Process. A role says what an element does functionally; it cannot turn a process into a resource. Motifs constrain both, so the node will not bind. |
| `StepRoleNeedsAProcessTypeShape` | Warning | This element plays a step role but carries no class from the process family (beam:Process, beam:Infer, beam:Transform, beam:Train, beam:Generate). Step nodes match on 'a/rdfs:subClassOf* beam:Process', so an element outside that family can never bind and the role has no effect. |
| `UserFacingOutputIsProducedShape` | Info | This user-facing output is not produced by any step. Output-side patterns (improper output handling, system prompt leakage, sensitive disclosure) all reach the sink through beam:produce, so none of them can see it. |
| `UserInputDeclaresReachabilityShape` | Info | This user input is not marked pair:PublicUserInput. Risks that depend on a path anyone can drive - unbounded consumption on a direct-prompting path - test for that role and will stay silent, which is correct for an internal assistant and a gap for a public endpoint. Say which it is. |
| `VectorStoreIsRetrievedFromShape` | Info | This vector store or index is not used by any retrieval step. The Vector-IR and RAG motifs both require a step that beam:use-s the store, so no retrieval-side finding can be raised about it. |

## 6. Business context vocabulary

A submitted document may carry a business process model (sBPMN 2.0) beside the
architecture. It joins by refinement and never by subsumption: a `bpmn:activity` is
not a `beam:Process`. What a process states about its data reaches the architecture
through `business_data_bridge.rq`, which marks the edge of the refined system and
leaves the rest to propagation.

| Term | What it does |
| --- | --- |
| `pair:BusinessFlowDerivation` | Business Flow Derivation |
| `pair:DataClassificationOption` | One entry in the list the business editor offers for classifying a data object or store. |
| `pair:SystemContextOption` | One entry the editor offers for a system's domain or purpose. |
| `pair:bandOrder` | Where a pool or a lane sits in the stack the diagram draws. BPMN keeps layout in BPMNDI, which sBPMN does not model, and bp:ordering is declared on adHocSubProcess for Parallel/Sequential - so neither can say this. A band with no order falls back to its name, which is how every band was ordered before one could be moved. |
| `pair:businessFollows` | business follows |
| `pair:carriedOutBy` | The steps of the refined system that do this activity's work. A link, never a subsumption: the activity stays a business activity, and no query reads it. |
| `pair:classifiesAs` | The DPV term this option writes onto a bpmn:itemDefinition. |
| `pair:contextFacet` | Which facet property this option writes: facet:hasDomain or facet:hasPurpose. |
| `pair:contextValue` | The term this option writes onto the beam:System. |
| `pair:meansPersonalData` | means personal data |
| `pair:realisedBy` | realised by |
| `pair:refinedBy` | The AI system that carries out this business activity: one box in the process diagram, expanded into an architecture graph. |
| `pair:targetInferred` | True where the bridge found the element itself rather than being told which one. A business annotation names its element with pair:realisedBy where the analyst knows it; where they do not, the category lands on the edge the association crosses. Only one of those is somebody's claim, and a reader has to be able to tell them apart. |
